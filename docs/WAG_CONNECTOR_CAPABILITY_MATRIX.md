# WAG Connector Capability Matrix

**One executive question this module answers: for any given metric, is it real, automatable, first-party evidence — or a Studio-only number no future agent should assume it has?**

Every row below was verified against Google's current, official API reference documentation (links inline per section), not assumed from prior general knowledge. Where a Studio-displayed metric has no confirmed API equivalent, it is marked unavailable rather than mapped to a similarly-named field that isn't actually the same thing. This is the permanent reference every future WAG OS specialist (Greenlight, Packaging, Hook & Retention, Audience Intelligence, Format Intelligence) should check before assuming a number is obtainable automatically.

**Revision, 2026-08-11 (same day):** the first pass of this matrix checked only the YouTube Data API and the YouTube Analytics API's targeted-query interface, and wrongly classified thumbnail impressions and impressions CTR as having no API path at all. Katie caught this and asked for direct re-verification rather than taking either claim on faith. There is a **third, distinct API surface** — the YouTube Reporting API (bulk report jobs, not the same interface as the Analytics API's `reports.query` calls) — that does expose real thumbnail-impression data. That correction, and a second claim (a `uniques` metric) that did **not** hold up under the same direct verification, are recorded in detail in the relevant rows and in "API source strategy" below.

**Scope:** this matrix covers what is available to WAG as the channel *owner* via OAuth. WAG OS's connector currently requests exactly two scopes — `youtube.readonly` and `yt-analytics.readonly` — per Katie's 2026-08-10 directive. All three API surfaces below (Data, Analytics, Reporting) are reachable under these same two scopes for non-monetary data; none of the newly-identified fields require a new OAuth grant. This matrix does not cover the monetary/revenue scope (`yt-analytics-monetary.readonly`), which WAG OS deliberately does not request today.

## Bucket legend

- **A — Directly available through the official API.** Real, queryable, first-party, at the granularity stated.
- **B — Available through the API, but with a real limitation** (lag, coarser granularity than Studio shows, requires combining multiple calls, or requires an approximation rather than an exact Studio-label match).
- **C — Available only through Studio's UI or a manual CSV export**, not through either public API.
- **D — Not reliably available anywhere**, or not documented by Google at all (includes Studio-only AI features with no data contract).

## API source strategy: three complementary surfaces, not one

WAG OS's YouTube intelligence layer should be designed around three genuinely distinct API surfaces, each with its own integration shape — conflating them was the root cause of the thumbnail-impressions error corrected above.

| Surface | What it's for | Integration shape | Scope needed |
|---|---|---|---|
| **YouTube Data API v3** | Metadata + current public stats (title, publish date, duration, current view/like/comment totals) | Simple REST GET, on-demand, already how `youtube-sync` works today | `youtube.readonly` |
| **YouTube Analytics API v2** | Targeted owner analytics — retention, traffic sources, demographics, subscribers, playlist performance — queried on demand per video/date range | REST `reports.query` GET calls, on-demand, same pattern as Data API, straightforward to add to the existing sync | `yt-analytics.readonly` |
| **YouTube Reporting API** | Bulk/historical report ingestion, including Reach metrics (thumbnail impressions/CTR) that the Analytics API does not expose at all | Job-based: create a job once, then periodically list and download generated report files (CSV/GZIP) — a scheduled batch pattern, not a simple query | `yt-analytics.readonly` (same scope already authorized — confirmed no new OAuth grant required for non-monetary reports) |

All three run under WAG OS's existing two scopes for non-monetary data. Every raw row ingested from any of the three must stay provenance-tagged with which surface it came from (`metric_source` already does this for Data/Analytics; a Reporting API ingestion path would add `youtube_reporting_api` as a fourth allowed value, alongside the existing `manual_export`/`derived_wag_os`) — never blended into a single undifferentiated "YouTube metrics" bucket.

## Ranked by business value (not by ease of implementation)

Per Katie's instruction not to blindly ingest everything — rank by what actually moves Greenlight, Packaging, Hook/Retention, Audience, Format Intelligence, or CEO/Chief of Staff reporting, not by which is cheapest to build:

1. **Thumbnail impressions + impressions CTR** (Reporting API) — the single highest-value gap for Packaging Intelligence specifically. Nothing else in the current or planned data answers "did the thumbnail/title actually get people to click," which is the core Packaging question. Worth the real integration cost of the job-based workflow.
2. **Audience retention curve** (`elapsedVideoTimeRatio` + `audienceWatchRatio`, Analytics API) — the core input for the Retention Operating System described in `WAG_EXECUTIVE_OPERATING_LAYER.md`. High value, already a simple on-demand query per video.
3. **Traffic sources** (Analytics API) — directly explains *why* a video over/underperformed (algorithm-driven vs. search-driven vs. suggested), which changes what Packaging/Format should conclude from any given result.
4. **Subscribers gained/lost** (Analytics API) — the clearest signal of which formats convert casual viewers into owned audience, feeding both Format Intelligence and the Owned Audience mission.
5. **Shorts/Live/long-form segmentation** (`creatorContentType`, Analytics API) — cheap to add (one query parameter) and immediately corrects any format-performance comparison that would otherwise blend Shorts and long-form incorrectly.
6. **Daily time-series likes/comments/shares** (Analytics API) — meaningfully deepens Hook & Retention work (when did engagement actually accrue, not just today's total) at low added cost since it reuses the existing batch query.
7. **Playlist performance** (Analytics API) — directly relevant given WAG Main's 11 real playlists, moderate value, low cost to add.
8. **Geography + age/gender demographics** (Analytics API) — real Audience Intelligence value, but lower urgency than the above until an Audience Intelligence specialist actually exists to consume it.
9. **Relative retention performance, end-screen source-level traffic** — useful supporting detail, not worth a dedicated build priority on their own.

**Not worth pursuing:** unique viewers and new-vs-returning viewers (confirmed unavailable), and granular per-element end-screen click data (confirmed unavailable at that granularity) — no amount of engineering effort makes these real.

## What this means for the historical-ingestion and intelligence-layer work ahead

Everything marked **A** or **B** above and not yet ingested is real, available, first-party evidence WAG OS is not yet capturing — ranked by actual business value above, not by ease of implementation. The current `youtube-sync` vertical slice deliberately proved provenance and storage correctness first, on a small batch, before expanding query surface — per Katie's original 12-point directive. Expanding to these fields is a scope decision for the historical-ingestion phase, not a capability question.

Everything still marked **D** (new-vs-returning viewers, unique viewers) is a genuine, permanent blind spot for any *programmatic* WAG OS system, now checked across all three API surfaces, not just one. These numbers only exist inside YouTube Studio's own UI. If a future specialist needs them, the only path is a manual Studio pull recorded as a dated, sourced snapshot (the same honest pattern already used in `WAG_MEASUREMENT_STANDARDS.md`) — never invented, estimated, or silently substituted with a similarly-named API field.
