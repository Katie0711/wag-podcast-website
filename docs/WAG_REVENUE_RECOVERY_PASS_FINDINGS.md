## 9. Minimal Revenue & Partnerships schema — FINAL, post-correction (2026-08-11)

**Corrected twice the same day.** The first FINAL draft (superseded, preserved in git history) collapsed two real structural risks Katie caught before migration: treating intermediaries as a parallel company universe, and a single `brand_id` that couldn't represent a cross-brand deal. This version fixes both, adds provenance, scope/rights, and payments structures Katie required, and adds the approval-workflow tables Section 37 (Consolidated Architecture) requires. **Table names are `revenue_`-prefixed to avoid any collision with existing tables.** This is the version actually migrated — Section 10 below records the live result.

### 9a. Companies, people, and roles — one company universe, role is per-deal

- **`revenue_companies`** — `id, name, domain, category, notes`. No `relationship_type` column here on purpose — a company's role (agency, direct client, licensee, etc.) varies by deal, so it's never stored as a fixed company-level attribute. Real seed: Kidoodle/A Parent Media Co., Epic!, Aha World, Pop&Boom, PolyBuzz — **Pop&Boom and PolyBuzz are two ordinary rows in the same table**, not a company plus a parallel "intermediary" entity.
- **`revenue_deal_parties`** — `deal_id, company_id, role` (`underlying_brand` / `agency_intermediary` / `direct_client` / `licensee` / `distributor` / `platform` / `advertiser` / `other`), `notes`. This is where Pop&Boom (role=`agency_intermediary`) and PolyBuzz (role=`underlying_brand`) both attach to the same real deal with different roles — the exact shape Katie asked for, without a second company system. `revenue_deals` itself carries no direct `company_id` — this table is the single source of truth for who's involved and how.
- **`revenue_people`** — `id, name, role, email, notes`. No `current_company_id` column — a person's current company is derived from `revenue_people_company_history` (the row with a null `end_date`), never stored redundantly in two places. Real seed: Leah Lindsay, whose real move from Kidoodle.tv to A Parent Media Co. mid-relationship is exactly the case this table exists for.
- **`revenue_people_company_history`** — `person_id, company_id, role, start_date, end_date` (null = current).

### 9b. Deals, multi-property routing, outcomes, and the approval workflow

- **`revenue_deals`** — `id, deal_type` (sponsorship / licensing / trade / other), `pricing_model` (flat_per_unit / royalty_recurring / one_time / custom — Epic is `flat_per_unit`, Kidoodle is `royalty_recurring`), `status` (the full real lifecycle per Consolidated §37a: `detected → verified → analyzed → needs_katie_review → approved_to_pursue / declined_by_katie → quoted → negotiating → closed_won / closed_lost`), `quoted_rate`, `agreed_rate`, `currency`, `initiated_by` (who/what first logged this — an agent name or "katie"), `created_at`.
- **`revenue_deal_brands`** — `deal_id, brand_id` (FK to the existing `brands` table), `is_primary`. **A join table, not a single column** — a WAG Main-only deal gets one row, a real cross-brand Main+Podcast deal gets two, a pure licensing deal (content-based, not channel-specific) can carry zero rows or point at whichever property the licensed content originated from. Epic's real seed row points at `WAG_MAIN` (the licensed catalog — animal-facts and horse-education shorts — originated there).
- **`revenue_deal_outcomes`** — one row per resolved deal (`deal_id` unique), `outcome_stage` (won / lost_declined_by_wag / lost_declined_by_counterparty / lost_no_response / lost_withdrawn), `outcome_reason` (the Consolidated §32 14-category taxonomy), `declined_by` (wag / counterparty / mutual / unresolved), `price_objection_occurred`, `counteroffer_occurred`, `brand_fit_issue` (all boolean), `resolved_at, notes`. **This is where the Pop&Boom case is represented exactly as required:** `outcome_stage=lost_declined_by_wag`, `outcome_reason=product_inappropriate_for_wag`, `declined_by=wag`, `price_objection_occurred=false`, `counteroffer_occurred=false`, `brand_fit_issue=true`.
- **`revenue_deal_events`** — `deal_id, event_type` (inbound_received / outreach_sent / reply / rate_quoted / negotiation / follow_up / invoice_sent / payment_received / overdue_detected / collections_action_recommended / collections_action_taken / declined / closed), `event_date, notes`. Provenance for each event lives in `revenue_evidence_links` (9c), not a bare text field.
- **`revenue_approvals`** — the centralized approval ledger required by Consolidated §37a: `table_name, record_id, action_type` (pursue_opportunity / send_message / approve_pricing / send_invoice / collections_action / sign_contract / other), `status` (needs_katie / approved / declined / superseded), `requested_by, requested_at, decided_by, decided_at, decision_notes`. One table, not an `approval_status` column duplicated across every entity — and the single query a future Needs Katie / Opportunities Requiring My Decision view runs against.
- **`revenue_outbound_messages`** — the first-class draft/send lifecycle Katie required and the prior draft was missing entirely: `deal_id, message_type` (initial_outreach / follow_up / counter / negotiation / renewal / payment_reminder / collections / licensing_outreach / decision_response / other), `status` (draft / awaiting_katie_approval / approved / sent / rejected), `drafted_by, drafted_at, approved_by, approved_at, sent_at, recipient, body`.

### 9c. Provenance and scope/rights — structural, not opaque notes

- **`revenue_evidence_sources`** — `id, source_type` (gmail_message / gmail_thread / uploaded_document / invoice_document / executed_agreement / manual_katie_provided / other), `gmail_account, gmail_message_id, gmail_thread_id, file_reference, description, captured_at`.
- **`revenue_evidence_links`** — `table_name` (restricted by CHECK to the real revenue_ tables that can carry evidence), `record_id, field_name` (nullable — can cite a whole row or one specific field, e.g. "price"), `evidence_source_id` (FK), `notes`. This is the generic answer to **"where did this fact come from"** for any material field (price, outcome reason, rights requested, payment terms, renewal date, amount owed) without adding a dedicated source column to every table.
- **`revenue_deal_terms`** — `deal_id, term_type` (deliverable / platform / usage_organic_vs_paid / whitelisting_spark / usage_term / territory / exclusivity / raw_footage / revisions / dedicated_vs_integrated / cancellation / payment_terms / other), `value_text, value_structured` (jsonb, for terms that need more than a string), `notes`. Structured and extensible — a new term type is a new row, not a schema migration — and never an opaque blob. This is deliberately short of full Contract Intelligence (no legal interpretation, just structured capture), matching Katie's explicit scope note.

### 9d. Invoices, payments, verification, pricing evidence, and commercial inventory

- **`revenue_invoices`** — `deal_id, invoice_number, period, amount_billed, currency, sent_date, due_date, source` (gmail / portal / accounting_system / direct_document / other), `status` (prepared / awaiting_katie_approval / approved / sent / void — the authorization lifecycle, per Consolidated §37a). **No `paid_date` or payment-status field here** — payment is tracked exclusively in `revenue_payments` below, so "was this invoice authorized to send" and "was this invoice actually paid" can never drift against each other by being stored twice.
- **`revenue_payments`** — `invoice_id, deal_id, amount, currency, payment_date, method, is_partial, notes`. Enables real AR/Collections: `revenue_invoice_ar_status` (a plain view, not a stored/stale field) derives `amount_received = SUM(payments)`, `remaining_balance = amount_billed - amount_received`, and `overdue` from `due_date`, per invoice — answering "who owes us, how much, how overdue, did they partially pay" from real rows, never inferred from an email saying "we'll pay."
- **`revenue_opportunity_verification`** — `deal_id, classification` (VERIFIED / LIKELY_LEGITIMATE / NEEDS_VERIFICATION / SUSPICIOUS / SPAM), `evidence, classified_at`.
- **`revenue_pricing_evidence`** — `deal_id` (nullable — general market research isn't always tied to one deal), `evidence_tier` (WAG_OBSERVED / EXTERNAL_OBSERVED / INDUSTRY_BENCHMARK / MODEL_ESTIMATE, Consolidated §16a), `evidence_category` (current_wag_ask / relationship_specific_historical / accepted_deal_pricing / declined_countered_pricing / external_market_evidence / pricing_intelligence_estimate), `amount, currency, source, notes, is_relationship_specific` (boolean, **must be `true` for Epic's $345/video** — Section 13a — so a market-comparison query excludes it by default rather than relying on memory).
- **`revenue_commercial_inventory_items`** / **`revenue_deal_inventory_items`** — the structural hook for "what was offered vs. what actually sold" (Consolidated §1, §18), built now but **not seeded** — no real formal inventory exists yet per the Foundation doc, so populating this table would be inventing data. The structure exists so Offer & Package Intelligence can populate it later without another migration.

**What stays in Gmail/source documents, not duplicated:** full email bodies, attachments, contract documents, and live negotiation back-and-forth stay referenced via `revenue_evidence_sources`/`revenue_evidence_links`. Only the structured facts above get persisted.

## 12. Why the original recovery pass missed this thread — Gate 1 diagnosis

**Katie's question, directly: why did a real, substantive, 16-message negotiation get missed by a search built specifically to catch this category?**

**Ruled out first:** the original `sponsor_partnership` query for `GMAIL_LEGACY_INTAKE` did contain matching terms — "collaboration," "partnership," and "agency" all appear as bare OR terms in the actual query text, and Pop&Boom's subject line ("Collaboration inquiry: thewildadventuregirls x POP&BOOM") and body ("a KOL agency") match multiple of them directly. **This was not a keyword-recall failure — the search terms were broad enough.**

**Also ruled out:** a `max_results` cutoff. The original query requested `max_results: 20`; Gmail's raw result count actually returned was 15 — below the requested cap, not at it. If the cap itself were the limiting factor, the tool would have returned exactly 20, truncating a larger match set. It didn't. This rules out "the query matched more but we only asked for/kept the top N" as the mechanism.

**What the evidence actually shows:** all 15 results that *did* come back are dated Aug 6-10, 2026 — a tight, very recent window — with nothing older, despite the query's terms being broad enough to plausibly match real correspondence going back months (Pop&Boom's thread, Jul 15 - Aug 2, included). That pattern — a request for up to 20 results, a return of exactly 15, and every one of them from the newest few days — is not what "the query only had 15 true matches, ever" would look like, given how common these search terms are; it's consistent with real matching messages existing further back that never made it into the final response.

**The most plausible mechanism, given how the tool is actually built:** `gmail-recovery-search` fetches each matched message's full content in a second step (`mapWithConcurrency`), and any individual fetch that fails (`if (!msgRes.ok) return null`) is **silently dropped** — filtered out of the response with no error surfaced, no count logged, no signal to the caller that anything went missing. This session has already documented, independently and repeatedly, a real pattern of client-side network flakiness (calls that fail with connection-level errors while every call that actually reaches Supabase's edge functions succeeds, confirmed directly via server-side logs). If that same flakiness hit a few of this query's per-message fetches — plausibly including some of Pop&Boom's 16 messages, which would have appeared in Gmail's true match set for this query — they would vanish from the result silently, with the response looking indistinguishable from "these messages never matched."

**This is a real design gap, not a privacy problem.** The fix does not require loosening Gate 1's purpose-limiting scope (the query stays a bounded, caller-supplied search — never a full mailbox list) or weakening any privacy boundary. It requires the fetch layer to stop failing silently:
- Return a `fetch_failures` count (and the affected message IDs, not content) alongside `result_count`, so a caller can see "18 messages matched, 15 fetched, 3 failed" instead of a bare, indistinguishable 15.
- Retry a failed individual fetch once before giving up, given the failures are known to be transient/client-side rather than server-side.
- Log fetch failures to `activity_log` alongside the existing sanitized query/result-count summary, so a pattern of silent loss would be visible in aggregate even if no one happens to catch a specific miss by name, the way Katie did here.

**Status: implemented and verified, 2026-08-11 (same day as diagnosis).** All three items above are live in `gmail-recovery-search` (version 3), backed by a new pure, unit-tested module (`reliability.ts` / `reliability.test.ts`, 8 passing regression tests proving a simulated failed fetch can never silently disappear). The response now carries `messages_matched`, `messages_fetched`, `messages_failed`, `complete`, and `failed_message_ids` (opaque IDs + failure reason, never content); a `retry_ids` mode allows re-fetching specific previously-failed IDs without re-running Gate 1's search. This is a reliability/observability fix scoped to the tool's own fetch layer — it changes nothing about what the tool is allowed to search or return, and required no change to the account scopes, the query-required design, or any other part of the Email Intake architecture's privacy model.

**Regression verification, run against the live fixed function:** the exact Pop&Boom query (`popboomlab.com OR from:alexzhang@popboomlab.com OR to:alexzhang@popboomlab.com`, `GMAIL_LEGACY_INTAKE`, `max_results:25`) was re-run. Result: `messages_matched: 16`, `messages_fetched: 16`, `messages_failed: 0`, `complete: true` — the full thread (`threadId 19f669167a66c816`) recovered in one pass, chronology matching Section 11 exactly. The fix is confirmed working on the real case that exposed the original bug, not just in unit tests.

**The general principle this instantiates is now permanent WAG OS policy, not specific to Gmail:** absence of retrieved evidence is never evidence of absence when retrieval was incomplete or failed — every future connector inherits this requirement. Recorded in `WAG_MASTER_OPERATING_SYSTEM_DIRECTIVE.md` §58 and cross-referenced in `WAG_REVENUE_EMAIL_INTAKE_ARCHITECTURE.md`'s Gate 1 description.
